Before adding the new service, ask whether the old one can do the job.

Before making the option configurable, ask whether anyone needs to choose.

Before implementing the workaround, find out whether its original cause still exists.

These are excellent assignments for an AI tool. They may even result in less code, which will make the productivity demonstration harder to photograph.

I want cheaper implementation to buy us more comparison and less attachment. Try the simpler design. Inspect the trade. Discard the elaborate draft if it doesn't justify what we'd have to maintain.

The same applies to existing code. An agent can help find duplicated rules and migration leftovers. Removal still needs evidence: consumers, actual use where available, and the reason the path existed. A rare operation isn't unused just because it escaped a search.

Give that work an owner and time in the plan. Faster generation won't spontaneously turn into cleanup. Left to itself, the available time will fill with more features and the abstractions they rode in on.

Reduction should preserve behavior and understanding. Compressing a function into a clever line doesn't count. Retiring a redundant path and the instructions required to maintain it does.

The repository has enough ways to become larger. I'd like to sponsor a few in the other direction.
